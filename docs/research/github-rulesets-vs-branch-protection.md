# GitHub rulesets vs classic branch protection

Research for [issue #4](https://github.com/Quattordici/Setpoint/issues/4). Checked on 2026-11-08.

**Question.** For each rule in the candidate neutral set (minimum reviewers, required status checks, conversation resolution, allowed merge types, protecting the default branch from force-push and deletion), how is the rule expressed in repository rulesets and in classic branch protection? Which plans support it? How do the two mechanisms interact when both exist? What do Octokit.NET and Octokit.GraphQL cover for rulesets?

**Short answer.** You can express every rule in the set with both mechanisms except allowed merge types. Classic branch protection has no merge-method field. There, merge types are only a repository setting (`allow_merge_commit` / `allow_squash_merge` / `allow_rebase_merge`). Rulesets add a per-branch `allowed_merge_methods` parameter on top of that setting, and the two are combined: a merge needs a method that both allow. The plan rules are the same for both mechanisms: public repos on Free; public and private repos on Pro, Team and Enterprise Cloud. On GHES, rulesets need 3.11 or later and the ruleset merge-method parameter needs 3.17 or later. Every supported GHES (3.19 to 3.22) has everything. If both mechanisms target a branch, GitHub combines them and the most restrictive version of each rule wins. Neither has a priority over the other. Octokit.NET (v14.0.0, latest) has **no rulesets support at all**, only classic branch protection. Octokit.GraphQL (0.4.0-beta, last commit Oct 2024) has generated ruleset types and mutations, but its model has no `allowedMergeMethods`.

Notes on the table:

- **Plan text for rulesets:** "Rulesets are available in public repositories with GitHub Free and GitHub Free for organizations, and in public and private repositories with GitHub Pro, GitHub Team, and GitHub Enterprise Cloud" [4]. The text for protected branches is the same, with GitHub Enterprise Server added [5]. So **a private repo on Free gets neither mechanism**.
- **Organization-level rulesets** (one ruleset that targets many repos) are for Team and Enterprise customers [13]. The `evaluate` enforcement mode (dry run with Rule Insights) is "only available with GitHub Enterprise" [14]. Repository-level rulesets support `active` and `disabled` on every plan that has rulesets [14].
- **GHES ruleset version:** the docs feature flag `repo-rules` is gated `ghes: '>3.10'` [6], and the ghes-3.10 OpenAPI description has no `/rulesets` paths while 3.11 has them [9]. So rulesets need **GHES 3.11+**. The supported GHES releases today are 3.19, 3.20, 3.21 and 3.22 [15], so every supported GHES has all five rules in both mechanisms.
- **GHES `allowed_merge_methods`, 3.11 anomaly:** the archived ghes-3.11 description includes `allowed_merge_methods`, but 3.12 to 3.16 do not, and 3.17+ do [9]. Archived descriptions are not reliable here, so the exact first GHES version is **unconfirmed**. Treat it as **3.17+**.
- **Review-count range differs:** rulesets allow 0 to 10 [2], BP allows 0 to 6 [3]. A neutral rule that asks for 7 or more reviewers cannot be expressed with BP.
- **Status-check source pinning:** both mechanisms can pin a check to a GitHub App, with `integration_id` in rulesets and `app_id` in BP [2][3]. In BP, `app_id: -1` means any app [3].

## Allowed merge types: repo setting vs ruleset rule

- The **repository setting** (`allow_merge_commit` / `allow_squash_merge` / `allow_rebase_merge`) says which merge buttons exist for the repo as a whole [10][16].
- The **ruleset parameter** `pull_request.allowed_merge_methods` limits the merge methods for PRs into the targeted branches. The docs say: "the targeted branches may only be merged based on the allowed type. Additionally if the repository has disabled a merge method and the ruleset required a different method, the merge will be blocked" [1]. The merge-methods page warns that "Merge methods set on the repository that conflict with the merge method rule will prevent merging" [16].
- **Result:** a PR into a branch can use only the methods that the repo setting allows **and** that every applicable ruleset allows. If none is left, the PR can't be merged.
- Classic branch protection has no merge-method control. Its only related field is `required_linear_history`, which in effect rules out merge commits [3][1].

## How the two mechanisms interact

- **They layer, and all applicable rules apply.** "Rulesets and branch protection rules can both protect branches in a repository. They work alongside each other, and all applicable rules are enforced." [11]
- **Most restrictive wins, with no priority.** "A ruleset does not have a priority … If the same rule is defined in different ways across the aggregated rulesets, the most restrictive version of the rule applies. As well as layering with each other, rulesets also layer with protection rules targeting the same branch or tag." [11] The docs' own example: a ruleset that requires 3 reviews plus BP that requires 2 means 3 reviews are required [11].
- **Cardinality differs.** "Only a single branch protection rule can apply at a time … This restriction does not apply to rulesets." [8] Many rulesets can target one branch, up to 75 per repo and 75 per org [11].
- **Bypass is configured per mechanism.**
  - **Rulesets:** `bypass_actors[]` with `actor_type` ∈ `Integration`, `OrganizationAdmin`, `RepositoryRole`, `Team`, `DeployKey`, `User`, and `bypass_mode` ∈ `always`, `pull_request`, `exempt`. `exempt` skips the rules and writes no bypass audit entry [2]. If nobody is on the list, nobody bypasses, admins included [17].
  - **Classic BP:** by default its rules **do not apply to repo admins** or custom roles with "bypass branch protections". To apply them to admins too, set `enforce_admins: true` ("Do not allow bypassing the above settings") [8][3]. Exceptions for PR requirements only go in `required_pull_request_reviews.bypass_pull_request_allowances` [3]. Bypass lists need an org-owned repo [8].
  - **Interaction (unconfirmed, inferred):** I found no primary source that says a bypass in one mechanism does or does not lift the other mechanism's rules. Because "all applicable rules are enforced" [11], the reading is that an actor must be able to bypass **both** to skip a rule defined in both. A BP rule without `enforce_admins` therefore does not weaken a ruleset that admins cannot bypass.
- **Reading the effective rules:** `GET /repos/{owner}/{repo}/rules/branches/{branch}` returns "all active rules that apply to the specified branch … regardless of the level at which they are configured (e.g. repository or organization)". It leaves out `evaluate` and `disabled` rulesets [18]. It is documented in terms of rulesets. Whether it also returns classic BP is **unconfirmed** (probably not). Read BP separately with `GET .../branches/{branch}/protection` [3].
- **Migration:** GitHub has a "convert branch protections to rulesets" feature on GitHub.com, and on GHES from 3.23 [19].

## Octokit coverage

### Octokit.NET (`Octokit` on NuGet)

- **Latest release:** `14.0.0` (NuGet versions end `13.0.0, 13.0.1, 14.0.0`) [20]. Tag `v14.0.0` is the current `main` HEAD, commit `7fa5b0f` from 2025-01-08 [21].
- **Rulesets: no support at all.** Searching `Octokit/**/*.cs` at that commit for "ruleset" finds nothing, and `ApiUrls.cs` has no `/rulesets` or `/rules/branches` route [21][22]. Issue [#2918](https://github.com/octokit/octokit.net/issues/2918), "[FEAT]: Rulesets (Tags and Branches)", was closed by the stale bot on 2025-10-29 with no implementation. Issue [#3084](https://github.com/octokit/octokit.net/issues/3084), "Add support for the Rulesets API (repository & organization)", is open and in triage (opened 2026-07-13), and says "Octokit.net has no RulesetsClient or equivalent".
- **Classic BP: supported** through `IRepositoryBranchesClient`: `GetBranchProtection`, `UpdateBranchProtection`, `DeleteBranchProtection`, the required-status-checks and review-enforcement sub-resources, and push restrictions [23]. `BranchProtectionSettingsUpdate` carries `RequiredStatusChecks`, `RequiredPullRequestReviews`, `EnforceAdmins`, `RequiredLinearHistory`, `AllowForcePushes`, `AllowDeletions`, `BlockCreations`, `RequiredConversationResolution` and `LockBranch` [24].
  - **Gap:** `BranchProtectionRequiredStatusChecksUpdate` only takes `strict` plus `contexts` (strings). It does not model `checks[]` with `app_id`, so it cannot pin a check to an app [24].
- **Repo merge settings: supported.** `RepositoryUpdate.AllowMergeCommit`, `AllowSquashMerge`, `AllowRebaseMerge` [25].
- **Workaround:** call the rulesets endpoints through Octokit's low-level `IConnection` / `IApiConnection` with your own DTOs (generic HTTP; I did not test this). Or use another client.

### Octokit.GraphQL (`Octokit.GraphQL` on NuGet)

- **Latest release:** `0.4.0-beta`, still prerelease [26]. `main` was last committed on 2024-10-07 [27].
- **Rulesets:** the generated model has `RepositoryRuleset` (with `BypassActors`, `Conditions`, `Enforcement`, `Rules`, `Target`) and the mutations `CreateRepositoryRuleset`, `UpdateRepositoryRuleset`, `DeleteRepositoryRuleset` [28][29]. The `RepositoryRuleType` enum includes `PullRequest`, `RequiredStatusChecks`, `NonFastForward`, `Deletion`, `MergeQueue` and more [30].
  - **Gap:** `PullRequestParameters` has only `DismissStaleReviewsOnPush`, `RequireCodeOwnerReview`, `RequireLastPushApproval`, `RequiredApprovingReviewCount` and `RequiredReviewThreadResolution`. It has **no `AllowedMergeMethods`**, because the schema snapshot predates it [31]. Whether today's live GitHub GraphQL schema exposes allowed merge methods is **unconfirmed** (not checked).
- **Classic BP:** the `CreateBranchProtectionRule`, `UpdateBranchProtectionRule` and `DeleteBranchProtectionRule` mutations exist [28]. GraphQL BP rules accept wildcard patterns, which REST does not [12].

## Implications for decisions

1. **Use rulesets as the primary GitHub backend for the neutral set.** They are the only mechanism that expresses all five rules, including per-branch allowed merge methods. They target the default branch symbolically (`~DEFAULT_BRANCH`), so a default-branch rename needs no change. They also allow 0 to 10 reviewers where BP allows 0 to 6. Their plan coverage is the same as BP on GitHub.com.
2. **Allowed merge types needs two writes on GitHub:** the repo setting (`PATCH /repos`) plus the ruleset `allowed_merge_methods`. Setpoint should keep them consistent, because a mismatch makes PRs unmergable. Decide whether the neutral rule means "repo-wide" (setting only) or "per target branch" (both writes).
3. **Classic BP fallback is needed only for GHES older than 3.11**, which is out of support. GHES 3.11 to 3.16 can't do the merge-method part of rulesets. If Setpoint supports only supported GHES releases (3.19+), it can skip a BP backend entirely.
4. **Existing BP on a repo will layer with Setpoint's rulesets.** Most restrictive wins, so a stricter leftover BP rule silently overrides the declared policy. Drift detection should read BP as well as rulesets, and either report BP or offer to remove or convert it.
5. **Free private repos get neither mechanism.** Setpoint should detect this, and report "unsupported on this plan" rather than failing on a 403 (the exact error status is unconfirmed).
6. **Bypass actors don't map one-to-one.** Rulesets enforce on admins unless they are listed. BP exempts admins unless `enforce_admins` is set. A neutral "who may bypass" concept has to be mapped per backend.
7. **Octokit.NET can't do rulesets.** Plan on hand-written DTOs over `IConnection` / `HttpClient` for `/rulesets`, or generate a client from the `github/rest-api-description` OpenAPI. Octokit.NET is still fine for repo settings and for reading BP. Octokit.GraphQL is prerelease, stale, and missing `allowedMergeMethods`, so don't depend on it for this.
